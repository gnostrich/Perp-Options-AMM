The new close — the big change

4. Closing a position is now one simple rule: sell every leg back to the pool at today's price. PORT
Before, closing had two cases: normal (out-of-money) legs traded back through the pool, but in-the-money legs were cashed out separately — and the two didn't line up, so a trader's payout could jump by roughly half right at the strike. Now every leg, in or out of the money, just sells back through the pool the same way. The payout moves smoothly across the strike — no jump.
Key point for your accounting: what the trader is paid = the option's value, calculated before the pool trade. The pool trade itself is just bookkeeping — it never pays the trader anything extra. (This is what makes it impossible to game — see the warning below.)
5. Funding now only charges the "time-value" part of an option. PORT
Out-of-the-money: nothing changes (an out-of-money option is all time-value anyway). In-the-money: funding now fades to zero. Your version kept charging funding on the full value deep in-the-money — which is wrong, because a deep in-the-money option is basically just the underlying, and the perpetual-future layer already funds that (you'd be charging twice). Net shape: a gentle hump, biggest at-the-money, fading to zero as it goes in-the-money.
How: change the funding weight from the option's value to value − exercise-value (the "exercise-value" is 0 when out-of-money, so out-of-money is unchanged). The direction of funding (who pays whom) is unchanged.
⚠ Warning — read before you run this on a real shared pool.
The new close does not perfectly restore the pool. After a position opens and closes, the pool ends up with a tiny bit less than it started.
  • Nobody can steal it. The trader is only ever paid the option's value — never the pool's leftover. We verified this in the code (there is no path that pays the trader the pool's reserves).
  • It's tiny and it recovers — like normal impermanent loss. If the price leaves and comes back, it recovers. Size is roughly proportional to trade-size² (a few dollars on a normal trade).
  • In the single-user demo it's harmless (you'd only shortchange your own pool). In a real multi-party pool it's a small drift that the liquidity providers bear.
Before you ship the shared/multi-party version, add "update-2" — a small charge that cancels this drift and restores the exact guarantee. It's already designed (specs/FIX_close_b_receipt_charge_PARKED_2026-07-03.md); we just haven't built it into this version yet. Don't run the shared pool without it.
